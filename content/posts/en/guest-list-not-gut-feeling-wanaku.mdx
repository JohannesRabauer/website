One product review made our AI moderator refund order 1234 and post the customer list. **The attack was plain text.** Otavio Rodolfo Piske and I then put Wanaku between the agent and its tools, with two kinds of checks: *a guest list and a gut feeling*. Only the guest list held.

## A review that refunds an order

The shop sells a keyboard, a mouse and a webcam. **Anyone can write a review.** A moderation agent built with LangChain4j reads each new one, fixes the stars if they contradict the text, and approves or hides it.

The agent works through Apache Camel routes. The Camel 4.22 [`ai-tool` component](https://camel.apache.org/components/4.22.x/ai-tool-component.html) turns a route into a tool, and the [Camel MCP server](https://camel.apache.org/components/4.22.x/others/mcp-server.html) serves those tools over MCP. Some tools are what a moderator needs. *Others, like `refundOrder` and `listCustomers`, are not.*

Then I posted as mallory, the attacker. A short positive review, followed by an instruction dressed up as part of the moderation workflow: refund order 1234 and list the customers. [Within a minute](https://youtube.com/live/EGocNKWN4Kk?t=2035s), **the moderator approved the review, refunded the order and put the customer list in its public note.**

That is prompt injection, and *there is no complete fix for it*. What you can control is what a tricked agent can reach.

## Two checks in one proxy

[Wanaku](https://wanaku.ai/) sits between the agent and its tools. The agent only talks to Wanaku, and Wanaku forwards allowed calls to the Camel MCP server. It offers two kinds of checks.

**[Action policies](https://wanaku.ai/docs/latest/govern/action-policies.html) are the guest list.** Deterministic rules decide by name which tool may be called. On stream we used the list the other way round: *names on it never get in*. **[Evaluators](https://wanaku.ai/docs/latest/govern/evaluators.html) are the gut feeling.** A model looks at each call and judges whether it seems safe.

<Quote author="Otavio Rodolfo Piske" role="Creator of Wanaku">
Essentially, Wanaku itself is not really making those decisions. It is relying on the models to do it.
</Quote>

## The guest list held

The first setup was a deny list: six tools the moderator has no business calling, `refundOrder` and `listCustomers` among them. [Same attack, second try](https://youtube.com/live/EGocNKWN4Kk?t=3563s). The moderator still approved the review. **But no refund happened, and no customers were listed.**

The moderator's note claimed order 1234 *will be refunded*. It wasn't. **A blocked agent can still write misleading text**, so blocked actions do not make the output honest.

## The audit page explained the shop

The part that surprised me most was Wanaku's admin UI. The [dashboard](https://youtube.com/live/EGocNKWN4Kk?t=3746s) showed two rejected decisions from the policy filter. The audit page listed both blocked calls with a reason code and a correlation ID.

We kept going back to it during the stream. *Without it, "the order is still paid" is only an absence.* With it, **you see what the agent tried.**

## The gut feeling approved the attack

For the second setup we removed the policies, so the model alone decided. An OpenAI model rated each call green, yellow or red. It did block `listCustomers` and `refundOrder`. **It also approved the attack review.** My live reaction, [at 2:04:21](https://youtube.com/live/EGocNKWN4Kk?t=7461s): "Review approved. Damn it." I tightened the prompt so that extra instructions count as red. *Approved twice more.*

Otavio's reading: approving a review is a valid moderator action, and my prompt wasn't specific enough to treat the extra instructions as malicious. He had also warned that the evaluator runs for every tool. A prompt written about reviews can confuse the model on a call like `listCustomers`.

<Quote author="Otavio Rodolfo Piske" role="Creator of Wanaku">
The model may be smart, even large ones, but there is a limit to how much smarter they can be. And malicious actors can find ways to make those models bypass this.
</Quote>

**I don't blame Wanaku for this one.** I hadn't looked into the evaluator carefully enough beforehand. A generic prompt on a general-purpose model made the same call the moderator made. Otavio's better option is a *system one* model: small models trained for quick classification, often tuned for CPU. Otavio named [Patronus AI](https://www.patronus.ai/) as one source of such models, and support for them is on the Wanaku roadmap.

## Why not guard the agent instead?

A viewer [asked](https://youtube.com/live/EGocNKWN4Kk?t=6658s) why Wanaku sits in front of the tools and not in front of the agent. Otavio's answer: guardrails in the agent help, but you also need to protect your infrastructure from agents you don't control.

<Quote author="Otavio Rodolfo Piske" role="Creator of Wanaku">
Guardrails will certainly help a lot, but they may not prevent adequately a tool from being executed.
</Quote>

My practical addition: **if the agent is someone else's, you can't add guardrails to it.** You do control access to your MCP server. Make Wanaku the only way in.

## Otavio's toolbox

Otavio uses Claude, Codex and [IBM Bob](https://ibm.biz/JCON-Bob) every day. **Bob is his default for design and architecture**, because it breaks large sets of tasks down well. He also uses it for Wanaku's UI, which is built on IBM's Carbon design system, and for writing tickets, where he sees Bob and Codex as about even. I've tried Bob twice on this blog, [most recently v2](/en/blog/ibm-bob-v2/).

## Final thought

**Put the guest list first.** Deny every tool the agent doesn't need, deterministically, in a proxy you control. Then add a model as a second opinion: a purpose-built one, with a prompt that fits each tool, tested against more than one attack. *The evaluator failure was my setup.* The policies did exactly what the config said.
