## The reviewer who read the minutes

Most reviewers read the diff cold. Qodo has read *the minutes*. Before it comments on a pull request, it has indexed the whole codebase, every branch, past PR decisions and the commit history. It can pull in Jira or Linear tickets, docs from Notion or Confluence, and Slack.

That's why its findings reach **past the diff**. Filip showed a blast radius tag on each review, and cross-repo findings like a change that breaks a login service in another repository, linked to the exact line.

The problem it targets is one I recognize. Filip's scenario, [from 08:15](https://youtube.com/live/ljntagQDc5Q?t=495s): 200 developers with a coding agent each, writing **10 to 50 times more code**. Forty PRs a day instead of two or three. His question was who has the courage to click merge on that. My human colleagues take *one to five hours* per review round trip. That doesn't scale to forty.

## Don't let the agent grade its own homework

Filip's main argument for a separate reviewer, [at 12:17](https://youtube.com/live/ljntagQDc5Q?t=737s):

<Quote author="Filip Hric" role="DevRel Engineer at Qodo">
That agent cannot be just Claude Code reviewing Claude Code, right? Or Codex reviewing Codex, because sure it might find something, but ... they may share the same blind spot.
</Quote>

I pushed back a little. In one of my projects I have an "implement this issue" skill and a separate "review this PR" skill. **A fresh session with the same model still finds plenty** the implementing session missed. Filip took that as support for his point. He splits AI-assisted work into two jobs, **code generation and code verification**, and they have to be separate steps, whoever does them.

He added a second point I keep thinking about. [From 26:10](https://youtube.com/live/ljntagQDc5Q?t=1570s), he argued that *a rule loaded into the agent's context is not a rule enforced*. Someone still has to check.

## Review the ticket before the code exists

The part that changed my picture of Qodo came [at 57:59](https://youtube.com/live/ljntagQDc5Q?t=3479s). Filip drew the whole chain: ticket, plan, coding agent, review of uncommitted changes, PR agent. Today the review sits at the very end. Even with Qodo's review taking about two minutes, **the findings arrive after the PR**. He wants the same checks earlier: on uncommitted changes, on plans, and on tickets.

<QodoShiftLeftDiagram />

The [Agentic Toolbox](https://www.qodo.ai/blog/introducing-qodos-agentic-toolbox/) is how Qodo gets there. It's an MCP server, a CLI and a set of skills that give a coding agent the same tools that run on a PR. The agent has to call them; nothing interrupts on its own.

<Quote author="Filip Hric" role="DevRel Engineer at Qodo">
Bad description is going to result in a bad plan, which is going to result in a bad agent.
</Quote>

Then he showed it, [at 1:07:12](https://youtube.com/live/ljntagQDc5Q?t=4032s). In Codex, he ran the codebase wisdom skill on a Linear ticket for a workshop budget planner. **No code existed yet.** It flagged that the ticket duplicated existing duration logic and suggested `double` for money, where a repository rule requires `BigDecimal`.

Filip had written that ticket to fail on purpose. That backfired in a funny way: *with the Qodo plugin switched on, his agent refused to write the deliberately buggy app* until he turned it off. He has to remember to switch it off again before his next demo.

I already write my tickets with a coding agent. Calling a skill like this as the last step, to pressure-test the ticket before anyone implements it, is **one short step** from what I do today.

## Rules nobody wrote down

Every team has conventions that live only in people's heads. Qodo's *rule miner*, [shown at 1:30:16](https://youtube.com/live/ljntagQDc5Q?t=5416s), suggests rules from patterns in the code that were never documented. You apply a suggested rule to some repositories or the whole organisation, and it shows up in PR reviews and in the toolbox.

**Making invisible rules visible** is a good idea. Whether the mined rules are any good, we didn't test. It works the other way too: analytics show which rules everyone ignores, so you can weaken or delete them. Both of us agreed on the catch. If the signal isn't relevant, developers learn to ignore the comments.

Blast radius ties into where Filip thinks this goes. [Around 42:28](https://youtube.com/live/ljntagQDc5Q?t=2548s) he predicted that changes with a small blast radius will eventually be merged automatically. He was clear that this is his own guess, not Qodo's roadmap.

## Should we still read the code?

[At 43:42](https://youtube.com/live/ljntagQDc5Q?t=2622s) we got to the question I struggle with most. The merge button tempts me in a way it never did before AI. In one project I can't properly review the Next.js part, and that bottleneck pushes me toward letting an AI review it and merging.

<Quote author="Filip Hric" role="DevRel Engineer at Qodo">
It almost feels uncomfortable to say, like, maybe there are situations where you don't have to read the code.
</Quote>

Filip said it depends on context: healthcare and finance are not a startup. Reading line by line is a form of verification an agent can do as well, and human attention runs out. On stream I said that not reading the code is *a matter of time*. A day later, **I'm torn**. I believe the direction, but I'm not ready to stop.

We drifted into what AI does to learning [from 50:56](https://youtube.com/live/ljntagQDc5Q?t=3056s). Filip hears that AI rots everyone's brain and says his experience is the opposite. Mine is mixed: I expect to lose some Java detail and I've gained deployment and GitHub Actions skills. What counts now is asking good questions and actually reading the answers.

## No fix-it button

Qodo finds the problem, explains it and even writes a prompt you can paste into your agent. **It does not change code.** When I asked why there's no fix-it button, [at 1:36:11](https://youtube.com/live/ljntagQDc5Q?t=5771s), Filip said he expects agent loops to take over the fixing and eventually the merge click. Again, his assumption, not a promise. Today, *closing the loop is your agent's job*, and we didn't get to see that part live.

## Final thought

Qodo is best described as **a context layer for coding agents**: it brings the tickets, the history and the unwritten rules to whichever agent is working, at the ticket, during coding and at the pull request. The PR review is just the most visible place it shows up.

If I tried it tomorrow, I'd start small: *Qodo as a PR reviewer, with a human backing it up*. If that holds, I'd let it run on its own.
