## Not another LLM client

If you're shopping for a Java AI framework, put this one on the right shelf. I asked Luís whether it compares to the annotations in Spring AI or LangChain4j, [at 11:23](https://youtube.com/live/bm4BRjW0pUs?t=683s). He said it works **on another level** and is closer to [Embabel](https://github.com/embabel/embabel-agent).

<Quote author="Luís Neto" role="Committer, Jakarta Agentic AI">
In the Jakarta Agentic AI, you are creating agents that are going to run in a workflow, in our case, based in CDI events.
</Quote>

Spring AI and LangChain4j sit close to the LLM call. Jakarta Agentic AI *bundles calls into steps and chains them*. That's what I know from [LangGraph4j](/en/blog/langgraph4j-agents). The model itself is just a `LargeLanguageModel` facade you inject into whichever step needs it.

It's **a specification, not a framework**. Reza Rahman came up with the idea and invited Luís and other Payara people he knew from MicroProfile. The spec sits *outside the Jakarta umbrella* and doesn't follow its release schedule. Milestone 1 is out. Luís expects the first official version maybe next month. Payara Micro is the first implementation; Luís wrote that integration himself in [payara/Payara#8386](https://github.com/payara/Payara/pull/8386).

## Four strokes

Think of an agent as **a four-stroke engine**. Every run goes through the same strokes in the same order, and there are no hidden parts. Luís walked through them [from 18:07](https://youtube.com/live/bm4BRjW0pUs?t=1087s), one branch per step in [his fork](https://github.com/luiseufrasio/payara-ai-demo).

<JakartaAgenticFourStrokeDiagram />

- **`@Trigger`** starts the run. Your code fires a CDI event, Payara catches it. In version 1 there is *exactly one* trigger, and it's required.
- **`@Decision`** checks something. Returning true or an object continues. Returning *false or null skips straight to the outcome*.
- **`@Action`** does the work. Each action gets the previous action's result.
- **`@Outcome`** receives the last result. In the demo it stored the review so the REST resource could return it.

There can be **zero or many** decisions and actions. They run by an `order` attribute, or in source order without one. Failures go to `@OnException` methods, and *the handler for the most specific exception type wins*.

That's the whole spec you need to read code. I called it not complicated at all on stream. I still think so.

## Copilot read the manual

The demo app was a call for papers for a made-up "JCON Brazil 2030", running Payara Micro and Ollama in Docker Compose. Requesting a review only said the reviewer agent didn't exist yet. Luís suggested the prompt [at 08:21](https://youtube.com/live/bm4BRjW0pUs?t=501s): *give Copilot the spec* and ask for an agent that checks the scope, then reviews. I pasted the spec URL he dropped in the chat.

**It worked.** Copilot produced a clean agent for a brand-new standard from the spec alone. Luís's own version, written with Claude Code, looked much the same. Both passed the LLM in as a method parameter, where Luís would inject it as a field. *It still works.*

The interesting difference was the shape. Copilot built **two decisions and no action**: one for scope, one for quality, accepting at 7 out of 10. Luís, [at 36:57](https://youtube.com/live/bm4BRjW0pUs?t=2217s), called it possible, not wrong. For him, though, the review is an action.

<Quote author="Luís Neto" role="Committer, Jakarta Agentic AI">
The action is something you do, but it's not the verification. The decision is a verification.
</Quote>

I didn't get the difference at first. We boiled it down to one rule: **a decision can end the workflow, an action can't.** If your agent should always produce a score, that's an action. If a bad score should stop everything, Copilot's version is fine.

## A cake for JCON Brazil

After a rebuild the review ran, and the logs showed both decisions. Then we tested the scope check [at 40:25](https://youtube.com/live/bm4BRjW0pUs?t=2425s). *"Baking a cake" live on stage got accepted*, explained as a process that illustrates principles. "How to properly play soccer" got rejected. Luís joked that baking a cake might be closer to programming than soccer.

That's **the local model, not the spec**. Swapping in a paid model is a few lines in the MicroProfile config: provider, model, API key. Luís put it plainly: then you *spend your money*.

The exception handling held up under a real failure. [At 44:26](https://youtube.com/live/bm4BRjW0pUs?t=2666s) we stopped the Ollama container. The general handler Copilot had written returned a readable error. I added a second handler for the spec's `LLMException`, stopped Ollama again, and **the more specific handler fired**.

## Where version 1 stops

Simple has a price. A decision returning false *quietly skips every action*. I'm not calling that bad, but I prefer handling such things in code over an invisible workflow you just have to know. Luís said the team kept version 1 simple on purpose and welcomes new contributors.

There's **no way around the annotations** for now; the implementation finds the methods by reflection. Reza took inspiration from Jakarta Batch, and Embabel uses similar annotations. My problem with annotations is that you have to know them. Here that's four, so it's a small problem.

Each fired event gets *its own thread*, so one endpoint serves many users. Agents are fully independent today. To chain two, you fire the next event in your own code. Luís named a more flexible workflow for version 2, and **MCP and agent-to-agent communication maybe in version 3 or 4**.

## Final thought

The spec is small enough to learn from four annotations. It's small enough that a coding agent learns it from the spec URL. Luís had an explanation:

<Quote author="Luís Neto" role="Committer, Jakarta Agentic AI">
The agents are very good to read the specifications because the specifications are written in a well-formatted way.
</Quote>

If you're choosing a Java AI stack, **compare Jakarta Agentic AI with LangGraph4j and Embabel**, not with Spring AI or LangChain4j. It's a workflow layer on CDI. If you're already on a Jakarta EE runtime, *that may be the deciding point*. Our example was too simple to push it. Version 2 deserves a harder one, and Luís offered to come back for it.
